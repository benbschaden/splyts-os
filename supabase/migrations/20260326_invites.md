# Migration: invites

**File:** `20260326_invites.sql`

## What it does

Creates the `invites` table for managing pending team member invitations per organisation.

## Schema

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `organization_id` | UUID | FK → organizations |
| `email` | TEXT | Invited email address |
| `role` | TEXT | `'admin'` or `'member'` — role granted on acceptance |
| `token` | UUID | Unique invite token included in the invite link |
| `invited_by` | UUID | FK → auth.users — who sent the invite |
| `created_at` | TIMESTAMPTZ | When invite was created |
| `expires_at` | TIMESTAMPTZ | 7 days after creation |
| `accepted_at` | TIMESTAMPTZ | NULL until invite is accepted |

## Invite flow

1. Admin creates invite via `POST /api/invites` → row inserted, Supabase sends email with link containing `token`
2. Recipient clicks link → lands on `/invite/[token]`
3. If token is valid + not expired + not accepted: Supabase creates/logs in user, org membership created, `accepted_at` stamped
4. If token is expired or already used: user sees error message

## RLS

Only admins of the organisation can read, create, or delete invites for that org. The invite acceptance route uses the service role to bypass RLS (the accepting user has no org membership yet).

## How to run

Paste into Supabase SQL editor for the splyts-os project and execute.
