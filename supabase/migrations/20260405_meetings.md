# 20260405_meetings

## Summary
Adds three tables (`meetings`, `meeting_attendees`, `meeting_project_links`) that power the Meeting Intelligence feature: paste a transcript, process it with AI, review extracted decisions/actions/questions, and route relevant content to projects.

## Gherkin specs
Covered by `docs/features/meetings.md`.

## ADRs

### Why a separate table instead of a project?
Meetings span multiple projects. Storing them as a project record would create ownership confusion — a meeting about 5 topics would need to "belong" to one project arbitrarily. A standalone `meetings` table with a many-to-many `meeting_project_links` table allows one meeting to surface in multiple project Meetings tabs without duplication.

### Why store extracted output as JSONB?
The extraction schema (decisions, action items, questions) may evolve as the prompts improve. JSONB avoids migrations every time the output shape changes. The types are documented in code (`MeetingRow` in `lib/queries/meetings.ts`).

### Why attendee-scoped RLS?
A 1:1 meeting should not be visible to the rest of the company. Each meeting defaults to `attendees_only` visibility. The creator can promote it to `org_wide` (e.g. for all-hands notes). RLS enforces this at the database layer as a safety net; the service client in query functions adds a second layer.

### Why not soft-delete attendees?
Attendees are removed explicitly. A meeting without an attendee means that person was removed, not that they left the org. Keeping it a hard delete keeps the model simple. Meeting records themselves use soft-delete (`deleted_at`) so history is preserved.

## Design notes

- `meeting_attendees` uses a composite PK `(meeting_id, user_id)` — one user appears once per meeting.
- `meeting_project_links` uses a composite PK `(meeting_id, project_id)` — a meeting links to a project at most once.
- `relevant_summary` on `meeting_project_links` stores a short text describing what content from this meeting is relevant to the project; populated from the AI suggestion's `rationale` field when the user accepts.
- The `suggested_project_links` JSONB column on `meetings` stores the raw AI routing suggestions before the user accepts. Accepted routing creates rows in `meeting_project_links`. The suggestions column is kept for re-review purposes.
- `meeting_attendees_select` policy uses a minimal check (self or added_by) to avoid a policy cycle — the application uses the service client for all attendee queries.
